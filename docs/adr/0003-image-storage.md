# ADR 0003 — Фото объектов во внешнем S3-совместимом хранилище

- **Дата:** 28.09.2026
- **Статус:** предложено, нужен аккаунт хранилища

## Контекст

У объекта 10–20 фотографий, и их загружает агент. Render на обычном Web Service не даёт
постоянного диска: файловая система контейнера очищается при каждом редеплое, а деплой
случается несколько раз в день. Значит, «просто положить в `public/uploads`» означает
потерять фотографии, причём незаметно — карточки станут пустыми через сутки.

## Решение

Файлы кладём в S3-совместимое внешнее хранилище, в базе держим только ключ объекта
(`PropertyImage.storageKey`). Рекомендация — Cloudflare R2: S3-совместимый API, нет
платы за исходящий трафик, бесплатного объёма хватает на десятки тысяч фотографий.

Загрузка идёт по presigned URL: браузер отправляет файл в хранилище напрямую, наш
сервер выдаёт только подпись. Так фотографии на 10 МБ не проходят через инстанс Render.

## Альтернативы

**Render Disk.** Даёт постоянный диск, но привязывает сервис к одному инстансу и
мешает горизонтальному масштабированию. Для каталога с фото это лишнее ограничение.

**Supabase Storage.** Работает, но тянет в проект вторую платформу ради одной функции —
Postgres уже на Render.

**Хранить в Postgres как bytea.** Раздувает базу и бэкапы, отдача картинок через
приложение съедает инстанс. Нет.

## Последствия

- До появления ключей и бакета загрузка фото не работает: в карточке видны плашки, а в
  `PropertyImage` пусто. Это осознанная заглушка на время MVP, а не забытая функция.
- Нужны переменные окружения: endpoint, бакет, ключ и секрет. В репозиторий они не
  попадают.
- Понадобится генерация превью: отдавать оригинал на 5 МБ в сетку каталога нельзя.
  Решим отдельно, когда хранилище появится.
