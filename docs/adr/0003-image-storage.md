# ADR 0003 — Фото объектов во внешнем S3-совместимом хранилище

- **Дата:** 28.09.2026
- **Статус:** на время демо — байты в Postgres; объектное хранилище отложено

## Контекст

У объекта 10–20 фотографий, и их загружает агент. Render на обычном Web Service не даёт
постоянного диска: файловая система контейнера очищается при каждом редеплое, а деплой
случается несколько раз в день. Значит, «просто положить в `public/uploads`» означает
потерять фотографии, причём незаметно — карточки станут пустыми через сутки.

## Решение

Файлы кладём в S3-совместимое внешнее хранилище, в базе держим только ключ объекта
(`PropertyImage.storageKey`). Рекомендация — Cloudflare R2: S3-совместимый API, нет
платы за исходящий трафик, бесплатного объёма хватает на десятки тысяч фотографий.

Загрузка идёт по presigned URL: браузер отправляет файл в хранилище напрямую, наш
сервер выдаёт только подпись. Так фотографии на 10 МБ не проходят через инстанс Render.

## Решение на время демо (28.09.2026)

Заказчик собирает демо-стенд, и отдельная база под сервис появится позже. Для этого
этапа снимки лежат **в Postgres**, таблицей `ImageBlob`: не нужен ни аккаунт, ни ключи,
ни второй сервис, а демо должно выглядеть наполненным уже сегодня.

Что сделано, чтобы это не стало ловушкой:

- **Отдельная таблица, а не колонка в `PropertyImage`.** Иначе выборка списка снимков
  тащила бы мегабайты там, где нужны только порядок и размеры.
- **Ключ несёт префикс бэкенда** — `db:<id>`. Переезд в объектное хранилище — это новый
  префикс и новый резолвер в `imageUrl`, без правки модели и страниц.
- **Сжатие при загрузке:** не больше 1600px по длинной стороне, WebP, качество 80.
  Снимок с телефона это 3–5 МБ и 4000 пикселей, а в интерфейсе он никогда не
  показывается больше 1600 — хранить разницу значит платить за то, чего не увидят.
- **Предел 15 фотографий на объект.**
- **`Cache-Control: immutable` на год.** Байты никогда не меняются: новый снимок
  получает новый идентификатор, поэтому браузер не приходит за той же картинкой дважды.
- Маршрут `/api/images/<id>` публичный: он понадобится на странице подборки для
  клиента, у которого сессии нет. Идентификатор — cuid, угадать нельзя, внутренних
  полей объекта картинка не раскрывает.

Порог, за которым нужно переезжать: сотни объектов. Пятнадцать снимков по 300–500 КБ
это 5–7 МБ на объект, то есть сто объектов — около полугигабайта, и бэкапы примерно
удваивают.

## Альтернативы

**Render Disk.** Даёт постоянный диск, но привязывает сервис к одному инстансу и
мешает горизонтальному масштабированию. Для каталога с фото это лишнее ограничение.

**Supabase Storage.** Работает, но тянет в проект вторую платформу ради одной функции —
Postgres уже на Render.

**Хранить в Postgres как bytea.** На постоянной основе — раздувает базу и бэкапы, а
отдача через приложение занимает инстанс вместо CDN. На время демо это осознанно
принятый компромисс, см. раздел выше: цена перехода потом невелика, потому что ключ
несёт префикс бэкенда.

## Последствия

- Загрузка работает с первого дня демо: файлы идут в Postgres. Бакет и ключи нужны на
  следующем этапе, когда объектов станет много.
- Пока у объекта нет своих снимков, обложкой служит кадр из 3D-тура — см.
  `src/lib/tour-preview.ts`.
- Нужны переменные окружения: endpoint, бакет, ключ и секрет. В репозиторий они не
  попадают.
- Понадобится генерация превью: отдавать оригинал на 5 МБ в сетку каталога нельзя.
  Решим отдельно, когда хранилище появится.
